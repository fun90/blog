# 博客写作与排版规范

## 写作流程

局部改动直接修改，随后按完成判据验收。新稿或结构性改稿按以下步骤进行。

1. **写简报**。明确目标读者、读完能做什么、必讲内容和范围。沿用用户已给出的要求。
2. **先定样稿**。根据简报拟好标题、开头、章节顺序，以及最能代替一段说明的图或表草图（适用时）。只在有会导致全文返工的取舍且无法从现有信息判断时，请用户选定；否则按样稿继续写完。
3. **独立审稿**。新稿或结构性改稿完成后，请独立会话读简报、成稿和关键来源。编辑者解决发现的问题后再验收。独立会话不可用时，按下列标准自审，并在交付时说明。

### 审稿验收

- **标题和顺序**：标题覆盖全文，章节顺序符合读者完成任务的顺序。
- **读者能照做**：代入目标读者走一遍示例，指出需要猜测的步骤、缺失的前提或难复制的命令；图表和正文只保留各自有用的信息。
- **事实有依据**：核对影响操作的版本、默认行为、路径和命令。区分官方说明、本地实测和推断。
- **反馈可定位**：每个问题给出具体位置、读者会遇到的障碍和建议改法。无问题时直接说明通过。

## 结构与排版

- **系列编号**：正文分篇从「（一）」开始，数字格式的 slug 从 `01` 开始。放在首篇之前的导读、基础篇使用无编号的标题和 slug。
- **开篇定调**：前 2-3 句话直接点明背景与核心结论，不铺陈空话。
- **图文表格优先**：能用架构图、流程图或对照表格说清的内容，不写大段无序列表；技术栈或工具对比使用 Markdown 表格，复杂分层使用独立图表组件（如 `src/components/mdx/PiMagpieDiagram.astro`）。
- **文字精炼**：删掉「首先、其次、总而言之」等过渡废话；每段不超过 3-4 行，确保 30 秒内可扫读完重点。
- **组件复用**：提示与避坑用 `src/components/mdx/Callout.astro`，外链推荐用 `src/components/mdx/ToolCard.astro`。

## Frontmatter 与隐私

- 严格匹配 `src/content.config.ts`：`category` 仅限 `'工具经验' | '软件开发' | 'AI 工作流' | '折腾笔记'`。
- 不贴冗长的原始配置文件；只保留最小必要片段。
- 严禁写入私有凭据、Token、真实内网地址或端口，示例配置统一使用占位符（如 `<port>`）。

## 完成判据

合并本轮已明确的文字和图表改动，定稿后执行 `pnpm check && pnpm build`，确认 0 error，且文章 HTML 与 `dist/og/<slug>.png` 均已生成。

图表或页面布局有改动时，用浏览器检查窄屏和桌面显示。浏览器工具在安装或升级后做一次兼容性检查；发现版本不兼容时，使用已有的可用浏览器完成预览。
